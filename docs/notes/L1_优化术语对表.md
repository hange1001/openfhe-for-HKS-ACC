## 1. 主表

### 1.1 并行性（导师条目：数据并行 / 任务并行 / 流水线并行）

| 通用术语 | 一句话定义 | 本项目的实例 | 证据锚点 | 状态 |
|---|---|---|---|---|
| **数据并行**<br>(data parallelism) | 同一操作作用于无依赖的多份数据 | `n` 维：`N=4096` 个系数在 BConv 内**零依赖**；`j` 维（输出 limb）之间也零依赖。二者合起来 = GEMM 的 batch 维与 M 维 | L1L2 §2.1 的 GEMM 三元组 `(K=α_d, M=\|C_d\|, batch=N)`；task.yaml 1.3 `derived_mechanism` | ✅ |
| **任务并行**<br>(task parallelism) | 不同的操作同时执行 | `dnum` 个 digit 的 ModUp 相互独立——各自的 BConv 目标基不同、乘的 `evk_j` 不同，**只在 P4 之后才汇合累加** | L0闭卷 §3.1；符号表 §3；L1L2 §2.5 点 6 | 🟡 从未作为一个**并行维度**记账，只当作循环边界 |
| **流水线并行**<br>(pipeline parallelism) | 不同阶段在时间上重叠 | 两个层次：<br>① 算子级 `INTT → BConv → NTT` 三段<br>② HLS 级 `load / compute / store` 三段 | task.yaml phase4 步 4.1（117K→87K cycles）、4.2 | ❌ 只有 TODO 和一个未解释的目标数字，没进任何模型 |

> **注**：三种并行在本项目是**同一个循环嵌套的不同维度**，不是三种技术。
> 六层循环 `d(digit) / i(输入 limb) / j(输出 limb) / n(系数)` 中：
> `d` → 任务并行；`j, n` → 数据并行；`i` → 归约维（不可并行，只能树形化）；
> 流水线并行是**跨算子**的，不在这个嵌套里，它在 `INTT/BConv/NTT` 的串联上。

## 3. 三个空白的展开

### 3.1 延迟 vs 吞吐率 —— 最重要的一个

**症状**：L2 模型写成加法

```
T = Σ n_op·c_op  +  V/BW_eff  +  n_call·T_fixed
    └ 计算 ┘        └ 传输 ┘      └ 控制 ┘
```

**加号 = 假设三项完全不重叠。** 这个假设从未被声明过。

**更值得警惕的一点**：L1L2 §4 已经查实，CPU 路径的「总延迟」是**记账加总**而非独立计时
（`789+938+2512+231 = 4470` 精确闭合）。而 FPGA 路径的 8,229 μs 同样是
`H2D 1829 + kernel 5537 + D2H 863` 的精确加总——**同一个方法论问题，在另一条路径上重演。**

---

#### 【2026-08-13 已查证】源码结论

三条 offload 路径（`FpgaManager.h` 的 `Execute:386` / `ModOpBatchOffload:566` / `BConvOffload:614`）
用的是同一个模式：

```cpp
bo_in1.sync(XCL_BO_SYNC_BO_TO_DEVICE);   // XRT 同步 DMA，返回即传完
bo_in2.sync(XCL_BO_SYNC_BO_TO_DEVICE);
auto run = m_kernel_top(...);
run.wait();                               // 阻塞等 kernel
bo_out.sync(XCL_BO_SYNC_BO_FROM_DEVICE); // 同步 DMA
```

**结论 1：完全阻塞。** 无 `xrt::bo::async`、无多个 `run` 同时在飞、无双缓冲。
→ **并发度 = 1 确认**，加号模型成立。但成立的原因是**实现如此，不是物理限制**（ADR-008 的推论）。

**结论 2（意外发现，比结论 1 重要）：182.8 μs 不是墙钟，是下界。**
计时窗口开在 `Execute` 的第 415 行，每次调用在此之前/之后还有一段**完全未计时**的工作：

```
[未计时] xrt::bo × 3 次分配        ← 402-407 行，每次调用都重新分配
[未计时] bo_in1.write() / bo_in2.write()   ← host memcpy 进 BO
────────────────────────────────────
[计时  ] sync TO_DEVICE × 2        → h2d  = 40.6 μs
[计时  ] kernel + run.wait()       → kern = 123.0 μs
[计时  ] sync FROM_DEVICE          → d2h  = 19.2 μs
────────────────────────────────────
[未计时] bo_out.read()             ← memcpy 回 host
[未计时] xrt::bo × 3 次析构（释放）
```

→ `8.229 ms = 45 × 182.8` **既不是墙钟，也不是完整的记账加总——是一个不完整的记账加总。**

> ⚠️ **本节初稿的判断方向是错的**，留作记录：初稿写「若 H2D 与 kernel 有重叠，8.229 ms 是**上界**」。
> 实际是**没有任何重叠，但漏了计时**，所以它是**下界**——真实墙钟比 8.229 ms 更长。
> 教训：两个相反的偏差来源（重叠 → 高估／漏计时 → 低估）必须分开查，不能只想到一个就下结论。

**结论 3：得到一个新的 phase3 候选项——buffer 复用。**
`xrt::bo` 在每次调用**内部**构造（402-407 / 584-586 / 674-676）。
45 次调用 × 3 个 buffer = **135 次分配 + 135 次释放**。
`xrt::bo` 构造不是 malloc，是驱动 ioctl + 设备物理内存分配 + mmap，量级通常数十 μs。

| 候选项 | 改动范围 | 预测收益 |
|---|---|---|
| 修 OC（步 3.1） | OpenFHE 库 | 8% |
| B1 复合 opcode（步 3.3） | HLS + Host + 库 | 29% |
| **Buffer 复用（新）** | **纯 Host，一个文件** | **待测** |

修法：把 bo 提成成员变量，`Init` 里按最大尺寸分配一次，之后复用。
**不动 HLS、不动 OpenFHE 库、不动 opcode 协议——目前所有候选项里最便宜的一个。**

**确认实验（10 分钟，需 U55C 板卡）**：在 `Execute()` 函数体首尾各加时间戳，比
`Σ(整个函数墙钟)` vs `Σ(h2d + kern + d2h)`。差值即未计时部分。
若接近或超过 `T_fixed` 的 38 μs，buffer 复用就是当前性价比最高的改动。

**对 Amdahl 的影响**：若每次调用还有 `X` μs 未计入，真实分母是 `2748 + 15X`，
而 `X` **全部落在非计算一侧** → **未计时的部分越大，微架构优化的天花板越低。**
（「计算无限快 → 2.85×」这个上界会随 `X` 变小。）

**剩余要答的问题**：

1. ~~`FpgaManager` 的 offload 是阻塞的吗？~~ ✅ 已答，见上。
2. 把模型写出两个版本，都算一遍：

   这一项（占 DC 的 21%）大部分会消失。

#### 【2026-08-13】两项优化是超乘性的——所以要一起做，不能排队做

用 phase4 的目标（`117K → 46K` cycles，即片内 **2.55×**）代进单次 call：

| 方案 | 单次 call | 系统加速 |
|---|---|---|
| 现状 | 40.6 + 123.0 + 19.2 = **182.8 μs** | 1.00× |
| 只做微架构 | 40.6 + 48.2 + 19.2 = **108.0 μs** | 1.69× |
| 只做传输重叠 | max(59.8, 123.0) = **123.0 μs** | 1.49× |
| **两个都做** | max(59.8, 48.2) = **59.8 μs** | **3.06×** |

**`1.69 × 1.49 = 2.52 < 3.06`。** 单独做任何一个，收益都被另一个的存在低估。
这是 `+` 变 `max()` 的直接后果——**结论：这两项应一起排期，不是先后排队。**

**并且做完之后瓶颈换人**：`59.8 > 48.2` → PCIe 接管瓶颈。
（这回答了 L1L2 §7 灵魂拷问 #1 的兄弟问题：「X 驻留之后谁是新瓶颈」。）

> ⚠️ 未验证假设：59.8 μs 里约 38 μs 是 `T_fixed`（launch/setup），只有约 21.8 μs 是真传字节。
> **`T_fixed` 能否被重叠藏掉目前未知**——正是 step 1.2 实验 B 要标定的。藏不掉则「都做」那行明显变差。

### 3.2 负载均衡

**症状**：`α₀=2, α₁=1 → \|C₀\|=3, \|C₁\|=4` 这件事出现过三次（符号表 §3、L1L2 §2.3、task.yaml q5），
每次都被描述为「小参数产物，参数上推时选能整除的组合」——**这是一个规避建议，不是一个量化结论**。

**要答的问题**：

1. 若 `dnum` 个 digit **并行**处理（任务并行，见 §1.1），完成时间由最慢的 digit 决定：
   `T_parallel ∝ max_d(α_d + \|C_d\|)` 而非 `avg`。当前 `max = 5`，`avg = 5`——
   **等一下，`α_d + \|C_d\| = ℓ + K = 5` 对所有 `d` 恒成立**（符号表 §3）。
   那么不均衡到底出现在哪一步？→ **这是本节要先厘清的第一件事**：
   逐算子看，INTT 的工作量 ∝ `α_d`（2 vs 1，比 2:1），BConv 输出 ∝ `\|C_d\|`（3 vs 4，比 3:4），
   NTT 的工作量 ∝ `\|C_d\|`。总和相等，但**分算子看是不均衡的**——
   于是它在「每算子一次 offload」的 B0 边界下不构成问题，在 B1（每 digit 一次）下才构成问题。
2. 写出不均衡度的符号式：`imbalance(ℓ, dnum) = max_d W_d / avg_d W_d`，其中 `W_d` 按算子分别定义。
3. 代入 step 1.6 的候选参数点，验证「选能整除的 `(ℓ, dnum)`」这条建议的定量依据。

**影响**：这条直接决定 **B1 边界的收益是否被最慢 digit 拖累**——而 B1 是 phase3 步 3.3 的核心改造。
现在 3.3 的收益估计（-29%）没有考虑这一项。

### 3.3 流水线并行 + 分层 Roofline

**症状 A（流水线）**：phase4 步 4.1 写着 `117K → 87K cycles`，这个 87K 从哪来的没有记录。
若它是 `max(load, compute, store) × n_limb + 填充`，那就**已经是一个吞吐模型了**，只是没写成式子——
写出来，它就是 §3.1 那个 `max()` 版本在片内的对应物，两者是同一个道理在两级存储上的应用。

**症状 B（Roofline 分层）**：§1.4 的三个 AI 数字**属于三个不同的边界**，画在同一张 roofline 上会得出矛盾结论：

| AI 数字 | 分子（op） | 分母（byte 跨过哪条边界） | 对应的屋顶 |
|---|---|---|---|
| BConv **0.23 MAC/Byte** | `K·M = 15` MAC / 系数 | 片上 AXI：进 3 字 + 出 5 字 | **on-chip AXI 带宽**（512-bit @ 166MHz） |
| B0/B1/B4 **0.32 / 0.89 / 2.1 ops/byte** | 整条 ModUp 的 op | **PCIe**（host ↔ 加速器） | **PCIe 带宽**（~3 GB/s 实测） |
| NTT **`log N / 32`** | 蝶形运算数 | 单 limb 的读写 | 视放在哪级而定 |

**所以必须画分层 Roofline（hierarchical roofline），三条带宽屋顶**：PCIe / HBM / on-chip SRAM-AXI。
L1L2 §2.1 说「BConv 卡 I/O」用的是第三条屋顶；task.yaml §四说「AI 0.32」用的是第一条。
两句话都对，但它们**不是同一个瓶颈**，而现在的笔记里读起来像是同一个。

**这也正是本项目区别于 HERA/CiFlow 的地方**：HERA 假设密文已在 HBM，它的图上没有 PCIe 这条屋顶，
所以它看见的瓶颈是 NTT。把 PCIe 屋顶画出来，才是本项目的 Fig. 1。

**统一口径的三条硬规定（画图前必须先定）**：
1. **分子**：`op` 是按 MAC 计 1 还是按「模乘 + 模加」计 2？（`0.23 MAC/Byte` 与 `0.32 ops/byte` 目前不同源）
2. **分母**：明确标注跨过的是哪条边界，写进变量名，如 `AI_pcie` / `AI_axi`
3. **是否含 evk**：CiFlow 表 II 的 AI **含** evk 流量，本项目当前**不含** → 与文献对比前必须换算
   （task.yaml 1.3 `changes` 已列此项，本表把它升级为口径规定）

**影响**：这三条应写进 [L0_符号表.md](L0_符号表.md) §9，作为 step 1.3/1.4 的强制口径。

### D1–D2：延迟 vs 吞吐 + Amdahl

| 材料 | 范围 |
|---|---|
| **Stanford CS149 / CMU 15-418**（Kayvon Fatahalian，两校同一套课，讲义与录像公开） | 第 1–2 讲：*Why Parallelism? Why Efficiency?* 与 *A Modern Multi-Core Processor*（含 latency hiding / bandwidth limits） |
| **Hill & Marty, "Amdahl's Law in the Multicore Era"**, IEEE Computer, 2008 | 全文 4 页 |

**验收问题** —— ✅ **全部答完（2026-08-13）**

1. **8.229 ms 是墙钟还是记账加总？**
   → **都不是。是不完整的记账加总**（漏了 bo 分配与两次 memcpy），因此是**下界**。详见 §3.1。

2. **写成 Amdahl 形式，计算无限快时的上界？**
   → `T → 393 + 570 = 963 μs`，上界 `2748/963 = ` **2.85×**。
   与「修 OC 的 8%」的关系：

   | | 攻击了哪几项 | 收益 |
   |---|---|---|
   | 可用空间（计算清零） | 计算 | **2.85×** |
   | 修 OC | 计算的一小块（NTT 次数） | 1.09× |
   | OC + 片上驻留 | 计算 + 传输 + 控制 | 1.41× |

   **8% 本身就是一个诊断结果**：说明修 OC 没往主要矛盾上使劲。驻留能到 29% 是因为三项同时攻。
   → **Amdahl 的正确用法不是事后算加速比，是事前判断某个改动值不值得做。**

3. **Little's Law 的三个量？**
   → 并发度 **1** ／ 吞吐 **5470 calls/s** ／ 延迟 **182.8 μs**。三者自洽——
   但注意这是**循环论证**：`8.229 ms` 本来就是 `45 × 182.8` 算出来的，
   **现有数据既不能证明并发度=1，也不能证伪。** 真凭据来自源码（§3.1）。

> **由此得到的元结论**：并发度 = 1 时 `吞吐 = 1/延迟`，两者是同一个量。
> **「优化 throughput」这个说法在当前系统上还不成立**——必须先把并发度做出来，
> throughput 才成为一个独立的、值得单独优化的量。
