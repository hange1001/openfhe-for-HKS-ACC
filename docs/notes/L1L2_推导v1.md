## 0. 一句话结论

**三策略的排序不是策略本身的性质，是"BConv 与 NTT 的相对单价"的性质；而这个单价比由 ADR-008（无状态 opcode-RPC）决定。** 换句话说：一条 L3/L5 的微架构决策，在无人察觉的情况下决定了 L2 的策略胜负——这正是"体力活感"的根源：每层各自局部最优，但没人写下层与层之间的推导链。

附带四个必须先修的账目问题（§4）：表 5-4 内部不自洽，峰值缓冲数字是插桩虚构，R2 的定量入口当前不成立。

## 1. 三模型钉在 L0–L5 上：每个模型从哪一层取需求

姜的"设计 = 给定需求和约束下的逻辑推理"翻译到这个金字塔，是说**每个模型参数都必须有一个上游来源**。把它画实：

```
          需求/约束向下流                模型参数向上供给
L0 算法   CKKS HKS 公式          →  给出 α, dnum, sizeQl, sizeP 的合法取值域
   ↓
L1 算子   把公式切成"一次调用算什么"  →  给出 n_op, n_call, V(字节), peak(limb) 的【符号表达式】
   ↓                                    ← 约束来自 L3 的阵列形状 3×5 和 L5 的 T_fixed
L2 调度   循环序 + 存储分配          →  三模型合成 T(N,L,dnum)；输出策略胜负相图
   ↓                                    ← 约束来自 L4 的片上预算 B
L3 微架构 PE 阵列/蝶形/驻留           →  给出 c_op 单价（csynth 周期）
   ↓                                    ← 约束来自 L4 的时序与资源
L4 物理   时序/资源/布线              →  给出 f_clk、B_onchip、csynth→上板修正系数
   ↓
L5 系统   PCIe/XRT/driver            →  给出 T_fixed、BW_eff
```

**读法**：左边是"需求向下"，右边是"参数向上"。你现在缺的不是 L1/L2 的**知识**，是这条右边的**回路**——L3 你能给出 15,701 cyc，L5 你能给出 182.8 μs，但没有一个 L1 表达式把它们乘起来。所以每次实测出个数字，只能事后解释，不能事前预测。这就是体力活的定义。

**判据（可自查）**：一个数字如果不能回答"它是哪一层的哪个约束推出来的"，它就是拍脑袋常数。下文每个数字都带这个出处。

## 2. L1 推导：把 BConv 还原成 GEMM

### 2.1 核心还原

ModUp 对 digit `d`、输出 limb `p`、系数 `n`：

```
y_d[p][n] = Σ_{i ∈ D_d}  x_d[i][n] · W_d[i][p]   mod m_p
其中 x_d[i][n] = c[i][n] · Q̂⁻¹_{d,i} mod q_i     （所有 p 共享，只算一次）
     W_d[i][p] = PartQlHatModp[i][p]              （常数，host 预计算）
```

这就是 **Y = Wᵀ X**：

| GEMM 维 | HKS 对应 | 当前值 |
|---------|---------|--------|
| K（归约维） | digit 内的 tower 数 α_d | 2 / 1 |
| M（输出维） | 补基大小 \|C_d\| = sizeQlP − α_d | 3 / 4 |
| "batch"（长维） | ring 维 N | 4096 |

`define.h` 的 `LIMB_Q=3 × MAX_OUT_COLS=5` 脉动阵列，就是一个 **K×M 权重驻留 GEMM tile**。你在 L3 已经做了一个 NPU 的 PE array，只是从没在 L1 用 GEMM 的语言描述它——所以 NPU 那套 tiling/stationary 词汇一直没能迁移过来。

**算术强度**（每个系数 n）：读 K 字、写 M 字、做 K·M 次模乘加。K=3,M=5 时 = 15 MAC / 8 words = **0.23 MAC/Byte**。这是极低的强度——**BConv 结构上是访存受限，不是计算受限**。
交叉验证：csynth BConv = 8,232 cyc 处理 4096 系数 ≈ 2.0 cyc/系数；512-bit AXI 每拍 8 字，进 3 limb + 出 5 limb = 8 字/系数 = 1 拍/系数。8232 ≈ 2 × 4096 → **确实卡在 I/O 而非 PE**。3×5 阵列已经供过于求。

> **L1 推论 #1**：Gap#2（single-tower BConv）的收益**全部在输出侧**（M: 5→1），输入侧一字不省。所以它的收益上限是 D2H 流量，不是计算量。gap 分析里"计算 5×"的说法在 I/O 受限的现实下不成立。

### 2.2 唯一的复用机会

整条 ModUp 里只有一个复用点：`x_d[i][n]` 被**所有** p 共享。三策略的全部区别，就是**在哪里把它留住**：

| 策略 | 经典 dataflow 分类 | 留住的是什么 |
|------|-------------------|-------------|
| MP | 全物化（no stationary） | 全部 X 和全部 Y 同时在 |
| DC | digit-stationary（≈ input-stationary） | 一个 digit 的 X 留住，遍历它的全部 p |
| OC | output-stationary | 一个 p 的累加器留住，遍历全部 digit |

**这一点值得写进论文**：CiFlow 的 MP/DC/OC 就是 Eyeriss 式 stationary 分类在 HKS 上的实例。一旦承认这个同构，**设计空间的未占点不用猜，分类法直接给出**（§2.5）。

### 2.3 精确算子账（从代码数出来，不是查表）

参数：N=4096, sizeQl=3, sizeP=2, α=2, dnum=2 →
digit0 拥有 {q0,q1}（α₀=2），补基 C₀={q2,p0,p1}（\|C₀\|=3）；
digit1 拥有 {q2}（α₁=1），补基 C₁={q0,q1,p0,p1}（\|C₁\|=4）。
Σα_d = 3 = sizeQl ✓；Σ\|C_d\| = 7；每 digit α_d+\|C_d\| = 5 = sizeQlP ✓。

| 项 | DC | MP | 伪OC（现状） | 真OC（CiFlow） | 真OC+驻留 |
|----|----|----|-------------|---------------|-----------|
| INTT limb 数 | 3 | 3 | 3 | 3 | 3 |
| BConv 调用数 | 2 | 2 | 4 | **7** | 7（融合进复合 op） |
| BConv 输入 limb 数 | 3 | 3 | 6 | **10** | **3** |
| BConv 输出 limb 数 | 7 | 7 | 14 | 7 | 7 |
| NTT limb 数 | 10 | 10 | **7** | 7 | 7 |
| **offload 调用总数** | **15** | **15** | **14** | **17** | **8** |
| H2D limb 数 | 16 | 16 | 16 | 20 | **6** |
| D2H limb 数 | 20 | 20 | 24 | 17 | 10 |

真OC 的 BConv 调用数推导：Section1 有 sizeQl 个输出，每个由 (dnum−1) 个 digit 贡献 = 3×1 = 3；Section2 有 sizeP 个输出，每个由 dnum 个 digit 贡献 = 2×2 = 4；合计 **7**。
> **修正 gap 分析 §4**：那里写的 `(sizeQl+sizeP)×(dnum−1) + sizeP×dnum = 9` 把 Section2 数了两遍。正确值是 `sizeQl×(dnum−1) + sizeP×dnum = 7`。

**验证这张表**：表 5-4 报的 FPGA kernel 调用数是 DC 45 / MP 45 / OC 44。我算出的 15/15/14 与之**差恒为 30**，三策略全部对上。所以映射关系是坐实的：
```
kernel_calls = (INTT limb + NTT limb + BConv call) + 30
                └────── 本表推出 ──────┘        └ Precompute 之外 ┘
```
那 30 次里 ModDown 按结构应占 12 次（每个 poly：P 部 2 INTT + 1 BConv + 3 NTT，×2 poly）；**剩余 18 次目前无归属**（最可能是 `EvalFastKeySwitchCoreExt` 的 limb-MAC，理论 2×5×2=20，差 2 需查）。**控制模型的第一个待办就是把这 18 次钉死**，因为它占全部调用的 40%。

### 2.4 L1 推论 #2：真 OC 在 ADR-008 下必然更慢

看上表最关键的一行：**真OC 的 BConv 输入 limb 数是 10，DC 是 3**。

原因是 output-stationary 的经典代价——**输入重取（input re-fetch）**：每算一个输出 tower 都要重新读一遍该 digit 的全部 α_d 个输入 limb。CiFlow 的 regime 里这不要钱，因为 INTT 结果常驻 32MB 片上 SRAM。**在你的系统里，ADR-008 规定 opcode 是无状态 RPC，每次调用的输入都要重新过一次 PCIe。于是 CiFlow 的免费项在这里变成主导项。**

```
ADR-008（L3/L5 决策：无状态 opcode RPC）
        ↓ 蕴含
每次算子调用重新物化输入
        ↓ 蕴含
output-stationary 的复用收益全部被 PCIe 吃掉
        ↓ 蕴含
L2 层 DC 胜、OC 负                      ← 你实测到的现象
```

**没人写下这条链，所以 OC 的失败被归因成"实现没修好"，实际上修好了也一样慢（17 次调用 > 15 次，H2D 640KB > 512KB）。** 这是本次推导最重要的结论：**CP-005 修 OC 的收益天花板是负的，除非同时动 ADR-008。**

反过来说，这条链也给出了解法（表最后一列）：加一个"digit 常驻 + 逐 tower 输出"的复合 opcode（ADR-008 自己预留的"阶段 2 复合 opcode"路径），H2D 从 16 limb 掉到 6 limb（**2.7×**），调用数从 15 掉到 8（**1.9×**）。**这才是 OC 该赢的赢法，而且它是一条软硬协同 claim，不是测量报告。**

### 2.5 设计空间与未占点

三个自由度（沿用指南 A3，但取值域按 §2.2 的 stationary 分类补全）：

| 自由度 | 取值 | 已占 |
|--------|------|------|
| F1 循环序 | digit-major / tower-major / 全屏障 / **batch-major** | 前三个 |
| F2 粒度 | full-\|C_d\| / single-tower / **tile(M_t)** | 前两个（后者伪实现） |
| F3 驻留 | 无 / **X 驻留** / **W 驻留** / **Y 驻留** | 无 |

未占点，各一句话评价：

1. **tower-major + full-\|C_d\|**（介于 MP 与 OC）：无意义，既不省缓冲也不省重取，可直接排除——**这是设计空间扫描的价值：用一句话杀死一个点，比跑一次实验便宜。**
2. **X 驻留（digit 常驻片上）+ tower-major**：即 §2.4 的解法。3 limb = 96KB，URAM 4MB 绰绰有余。**最高优先级未占点。**
3. **W 驻留（QHatModp 常驻）**：W 只有 α×\|C_d\| ≤ 3×5 个 64-bit 常数，本来就驻留在脉动阵列里——**已隐含占用，说明你的 L3 早就做了一个 L1 决策而没记账。**
4. **tile 粒度 M_t ∈ (1, \|C_d\|)**：single-tower 让 3×5 阵列利用率掉到 20%（gap 分析 §5.2 已注意到）。M_t=2 或 3 是利用率与 D2H 流量的折中点，**没人做过，因为 CiFlow 是模拟器不关心 PE 利用率**。
5. **batch-major（R2）**：见 §5.2，当前前提不成立。
6. **ModUp ⊗ KeyMult 融合**：把 P4 的 `ĉ_d[p]·evk_d[p]` 拉进 p 循环。**注意：这是真 OC 的必要条件**——CiFlow OC 的"跨 digit 累加"累的是 `Σ_d ĉ_d[p]·evk_d[p]`，不是 `Σ_d ĉ_d[p]`（后者数学上无意义，不同 digit 乘不同 evk）。gap 分析 Gap#5 的字面描述在这一点上是错的。而当前代码 `EvalKeySwitchPrecomputeCore` 返回完整 `partsCtExt` 再交给 `EvalFastKeySwitchCoreExt`，**函数边界结构性地禁止了这个融合**。

## 3. L2 三模型实例化

### 3.1 计算模型

```
T_compute = Σ_op  n_op(策略) · c_op(N, 参数)
n_op ← §2.3 表；c_op ← csynth × 上板修正系数
```

| 算子 | csynth 周期 | @166.67MHz | 上板 | 出处 |
|------|-----------|-----------|------|------|
| CG-NTT / limb | 15,701 | 94.2 μs | ~127 μs | 补 4-2「NTT 471.0 (5L)」÷5 |
| INTT / limb | 同上 | 94.2 μs | ~127 μs | 同上 |
| BConv full（3→5） | 8,232 | 49.4 μs | ~67 μs | 补 4-2「BConv 49.4」 |
| BConv single-tower | ~3,600（估） | 21.6 μs | ~29 μs | gap §5.2 推算，**未实测** |

**上板修正系数 = 1.35**，推导：补 4-3 的 kernel 累计 5,537 μs / 45 次 = 123.0 μs/次；若 45 次全按 csynth 单 limb NTT 94.2 μs 算得 4,239 μs，比值 1.31；扣掉其中几次较便宜的 BConv 后约 **1.35**。
> 这个系数是本模型里唯一一个"整体拟合"的量，它把频率偏差 + AXI 仲裁 + 未建模的握手全部吞掉。**它必须随每个新参数点重新标定，不能当常数外推**——这是模型的已知弱点，写在这里而不是藏起来。

### 3.2 存储模型

**流量**：`V = (H2D limb + D2H limb) × 32KB`，limb 数取 §2.3 表。
DC/MP = 36 limb = 1,152 KB；伪OC = 40 limb = 1,280 KB；真OC = 37 limb = 1,184 KB；真OC+驻留 = 16 limb = **512 KB**。

**带宽**：从补 4-3 两点拟合 `T_dma = T_f + bytes/BW`：
- H2D：40.6 μs / 32KB → 取 T_f,H2D ≈ 30 μs, BW ≈ 3.0 GB/s（30 + 10.9 = 40.9 ✓）
- D2H：19.2 μs / 32KB → T_f,D2H ≈ 8 μs, 同 BW（8 + 10.9 = 18.9 ✓）
> **两点拟合，自由度为零，等于没有验证。** 787 MB/s 那个数字是 T_f 污染后的折算值，禁止入模型（指南 Part E #3 已警告）。要真标定必须扫 bytes（1/2/4/8 limb 一次传）——这是 F2 的必做实验，一次 10 分钟。

**缓冲——本节是三个模型里错得最离谱的一个。**

`MemoryTracker` 报的 DC 64KB / MP 128KB / OC 32KB，与代码实际持有的缓冲不符：

| 策略 | 插桩记录 | 代码实际持有的瞬态 | 差 |
|------|---------|------------------|----|
| DC | `alloc(sizeP × 32KB)` = 64KB | `partsCtCompl[part]` = \|C_d\| limb，max 4 → **128KB** | 2× |
| MP | 2×64 = 128KB | Σ\|C_d\| = 7 limb → **224KB** | 1.75× |
| 伪OC | `alloc(1 × 32KB)` = 32KB，且 `peak_p_towers = 1` 是硬编码常量 | `fullCompl` 是完整 \|C_d\| limb → **128KB** | **4×** |

根因：插桩用了 `sizeP`（=2）当单位，而 BConv 的输出基是**补基** `C_d`，大小 `sizeQlP − α_d` = 3 或 4，不是 sizeP。指南 B2 里写的 `peak_p_towers`：DC=sizeP / MP=dnum×sizeP / OC=1 **三个都错**，正确形式是：

```
peak_transient(DC)  = max_d |C_d|      = sizeQlP − min_d α_d
peak_transient(MP)  = Σ_d |C_d|        = dnum·sizeQlP − sizeQl
peak_transient(真OC) = 1               ← 只有 Gap#2 落地后才为真
peak_transient(伪OC) = max_d |C_d|     ← 现状，与 DC 相同
```

**并且三策略都漏了两个常驻项**：`partsCt`（3 limb = 96KB）与 `partsCtExt`（dnum×sizeQlP = 10 limb = **320KB**）。加上后真实工作集：

| | 瞬态 | 常驻 | 合计 | 相对 OC |
|--|-----|------|------|--------|
| DC | 128KB | 416KB | 544KB | 1.00× |
| MP | 224KB | 416KB | 640KB | 1.18× |
| 伪OC | 128KB | 416KB | 544KB | 1.00× |

> **伪OC 相对 DC 的峰值缓冲优势 = 0。** 报出来的 4× 是插桩虚构。

### 3.3 控制模型

```
T_control = n_call(策略) · T_fixed,          n_call ← §2.3 表
T_fixed = T_f,H2D + T_f,D2H + T_launch ≈ 30 + 8 + ε μs
```
`ε`（XRT launch + sync）**当前无法从已有数据分离**，因为补 4-3 的三段计时已经把它摊进 H2D/kernel/D2H 了。指南 B3 提的 batch 差值法是对的方法，但它需要 CP-013 的 batch 原型——**在此之前控制模型的 T_fixed 只有上界，没有值。**

opcode 派发开销：ADR-008 论证 <1%，本模型按 0 处理，依据成文于 [fsm_vs_cpu_scheduling.md](../papers/fsm_vs_cpu_scheduling.md)。✓（指南 Part C 该项可打钩）

### 3.4 合并预测 vs 实测

`T = T_compute + T_memory + T_control`，代入 §2.3 的 n 与 §3.1–3.3 的系数，只算 Precompute 区间：

| 策略 | 计算 | 传输 | 控制 | **预测** | 15/14 × 182.8 的实测折算 | 误差 |
|------|------|------|------|---------|------------------------|------|
| DC | 13×127 + 2×67 = 1,785 | 1,152KB/3GB/s = 393 | 15×38 = 570 | **2,748 μs** | 2,742 μs | +0.2% |
| MP | 同 DC | 同 DC | 同 DC | **2,748 μs** | 2,742 μs | +0.2% |
| 伪OC | 10×127 + 4×67 = 1,538 | 1,280KB/3GB/s = 437 | 14×38 = 532 | **2,507 μs** | 2,559 μs | −2.0% |
| 真OC | 10×127 + 7×29 = 1,473 | 1,184KB/3GB/s = 404 | 17×38 = 646 | **2,523 μs** | 未实现 | — |
| 真OC+驻留 | 1,473 | 512KB/3GB/s = 175 | 8×38 = 304 | **1,952 μs** | 未实现 | — |

误差 <2% —— 但**必须诚实说明这不算验证**：右列的"实测"本身是用同一个 182.8 μs/call 乘出来的，两边共享常数，属于自洽而非独立验证。真正的验证要等 F2 给出独立的 Precompute 区间上板计时。

**但这张表已经能回答一个真问题**：真OC 只比伪OC 快 0.6%，比 DC 快 8%；**而真OC+驻留比 DC 快 29%**。收益 90% 来自驻留，10% 来自 CiFlow 的五个机制。**这就是 ADR-003 要求的"修复投入上限"的定量答案：CP-005 单独做，天花板 8%。**

## 4. 口径对账（F2）：8.0–8.5 ms 与 4.47–5.99 ms 的谜底

Portfolio F2 悬了两套数字。它们不矛盾，是**两条不同的路径**，而且第二套数字是算出来的不是测出来的：

**第一套（表 5-4 的 4470/5170/5989 μs）= 纯 CPU 软件路径。**
证据：补 4-2 的表头明写「CPU 延迟为 host 侧 OpenFHE 软件实现（`SetFormat`/`ApproxSwitchCRTBasis`）的实测值」；其中 BConv 469 μs/call 正是 gap 分析 §5.1 标为"CPU 路径"的那个数。
另外，三策略的"总延迟"精确等于四个分项之和（789+938+2512+231 = 4470，MP、OC 同样精确闭合）——**说明"总延迟"是记账加总，不是独立计时**。因此 `ApproxModDown`、assemble、`SetElementAtIndex` 的拷贝全部不在其中。

**第二套（8.0–8.5 ms）= FPGA 路径，且 = n_call × 单次 offload 均值。**
补 4-3 直接记了 DC：H2D 1829 + kernel 5537 + D2H 863 = **8,229 μs**（45 次）。按各策略自己的单次均值折算：

| | 单次均值 | n_call | 乘积 |
|--|---------|--------|------|
| OC | 40.3+122.7+19.7 = 182.7 | 44 | **8.04 ms** |
| DC | 40.6+123.0+19.2 = 182.8 | 45 | **8.23 ms** |
| MP | 43.9+123.4+20.6 = 187.9 | 45 | **8.46 ms** |

**答辩材料里那个"OC 端到端 8.04 ms 最优"就是 44 × 182.7。** 它不是实测，是一个控制模型的输出——你早就在用控制模型了，只是没意识到，也没写下 `T ≈ n_call × T_fixed` 这个式子。而 OC"最优"的全部理由是**少发一次 kernel**（44 vs 45），领先 2.3%，落在单次均值的噪声里。

**由此得到的两条硬结论：**

1. **在 N=4096, L=3 这个参数点上，FPGA 路径（8.23 ms）比纯 CPU 路径（4.47 ms）慢 1.84×。** 这是诚实的、可发表的 regime 陈述——offload-bound regime 的存在证明——但它必须被明说，而不是让两套数字各自流传。
2. **两套数字的策略排序相反**：CPU 上 DC(4.47) < MP(5.17) < OC(5.99)；FPGA 上 OC(8.04) < DC(8.23) < MP(8.46)。这不是矛盾，是 §5.1 的机制。

## 5. 对 Portfolio 的三条修正

### 5.1 R1 的相图轴选错了

Portfolio 现在的轴是「参数规模 × 固定开销/带宽比」。但排序反转的真实机制是**BConv 与 NTT 的相对单价**：

| 平台 | BConv 单价 / NTT 单价（每 limb 输出口径） | 结果 |
|------|-------------------------------------|------|
| CPU | 938μs÷7 tower = 134 ／ 2512μs÷10 = 251 → **0.53** | 拿 BConv 换 NTT 不划算 → DC 赢 |
| FPGA | 67μs÷3.5 tower ≈ 19 ／ 127 → **0.15** | 拿 BConv 换 NTT 划算 → OC 赢 |

伪OC 相对 DC 的交易是：**多做 2× 冗余 BConv，换少做 3 次 limb-NTT**（10→7，因为 OC 在 INTT 前先把 Q 侧 EVAL 系数拷进 `partsCtExt`，省掉了 DC 的 Q 侧回程 NTT，见 `keyswitch-hybrid.cpp:508-516`）。这笔交易在 ratio=0.53 时亏，在 ratio=0.15 时赚。**交叉点就在 ratio ≈ 0.3 附近，而且你已经跨过它了。**

> **建议 R1 换轴**：横轴 `c_BConv / c_NTT`（目标平台性质），纵轴 `T_fixed / (limb_bytes/BW)`（offload 粒度性质）。这两个轴各由一个模型供给（计算模型 / 控制模型），比"参数规模"更接近机制，而且**你手上已经有两个平台的点了**（CPU 和 FPGA），相图从第一天就是内插不是外推。

### 5.2 R2 的定量入口当前不成立

ADR-005 的 `depth ≈ floor(B / peak_buf)` 依赖 OC 32KB vs MP 128KB 的 4×。按 §3.2：

- 32KB 是插桩虚构（真值 128KB，与 DC 相同）→ 4× 实际是 **1.0×**
- 加上 `partsCtExt` 等常驻项 → MP/OC = **1.18×**

**R2 在当前实现下是死的。** 复活路径唯一：`ModUp ⊗ KeyMult` 融合（§2.5 未占点 6），让 `partsCtExt`（320KB）永不物化，改为逐 tower 累加进 `cTilda0/1` 后立即流出。融合后 OC 工作集 ≈ 96（常驻 digit）+ 32（瞬态）+ 64（两个累加 tower）= **192KB vs DC 544KB = 2.8×**。R2 活，但倍数从 4 降到 2.8，且**必须先打破 `EvalKeySwitchPrecomputeCore` / `EvalFastKeySwitchCoreExt` 的函数边界**——这是比 CP-005 大得多的改动，应该在 Portfolio 里单独立项而不是挂在 CP-013 下。

### 5.3 F1（修 OC）的顺序应该改

现在 ADR-010 的顺序是 #3+#4 → #2 → #5，天花板按 §3.4 是 **8%**。而"X 驻留复合 opcode"一项就是 **29%**。
建议：**把驻留提到 #2 之前**，或至少先做一个只验证驻留收益的最小实验——不需要改 OpenFHE，只需要在 `top.cpp` 加一个 case 把 INTT 结果留在片上再连做 BConv（ADR-008 自己预留的"复合 opcode"路径）。一次综合就能拿到 R1 相图上最重要的那个点。

## 6. "算法到 GDS"：能力缺口与最小练习

先把话说清楚：你在 FPGA 上，链条终点是 bitstream 不是 GDS。**但可迁移的不是流程，是"每层的设计都能被上一层推出来"这个习惯。** 按层给缺口和最小练习：

| 层 | 现状 | 真正缺的能力 | 最小练习（各 ≤1 周） |
|----|------|------------|-------------------|
| L0 | 读过没推过 | 徒手推 ModUp 求和式，标注哪些量跨 p 共享 | 指南 A1 自查表，闭卷写一遍 |
| L1 | **空白** | 把算子写成 GEMM 三元组 (K,M,batch)，从循环序**数出** n_call/V/peak 的符号式 | 本文 §2.3 那张表，换 (N=2^14, L=6, dnum=3) 重算一遍，全部用符号不用数字 |
| L2 | 有实现无模型 | 三模型合成 + 预测**先于**实测 | 下次改代码前，先写下预测值和 ±15% 区间，改完再对——**这是把体力活变成研究的唯一动作** |
| L3 | 主力 | （不缺）但要学会**向上报价**：每个微架构决策换算成 c_op 交给 L2 | 给 CG-NTT / BConv 各做一张"单价卡"：参数 → 周期 → 上板 μs |
| L4 | HLS csynth，无 P&R | 时序收敛的**闭环**：csynth 估计 → 后端实测 → 修正系数 | 把 ADR-007 那个 −0.33 ns 跑完 Vivado P&R，得到第一个真实的 csynth→上板修正系数（现在 1.35 是拟合的） |
| L5 | 已通 | T_fixed 的**分解**能力 | bytes 扫描实验（1/2/4/8 limb），10 分钟，拿到真 BW 和真 T_f |

**GDS 那一段（若要补 ASIC）**：FPGA 缺的是 floorplan / CTS / DRC-LVS / power grid 这几件在 FPGA 里被工具隐藏的事。用 OpenROAD + Sky130 把你的 Barrett PE（单个乘法器 + 约减，几百门）跑到 GDS，一天的事，目的不是成果是**把 L4 的黑箱打开**。但优先级低于上表——**你现在最贵的缺口是 L1，不是 GDS。**
