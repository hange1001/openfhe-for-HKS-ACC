平台：Xilinx Alveo U55C (xcu55c-fsvh2892-2L-e)，时钟周期 6ns (166.67 MHz)

## 1a. BConv: PE阵列 (Systolic) vs 朴素实现 (Naive)

做法：保留当前 bconv.cpp 作为优化版（Systolic Array），另写一个 bconv_naive.cpp 用简单循环实现，分别综合对比。

### 综合结果对比

Naive BConv 延迟可从 csynth.rpt 直接推导（sizeP 是运行时参数，但各阶段 trip count 已知）：

| 阶段 | Trip Count | II | Iter Lat | 延迟 (cycles) |
|------|-----------|-----|---------|--------------|
| Load_W | 15 (LIMB_Q×MAX_OUT_COLS) | 1 | 2 | 17 |
| Load_Mod | 5 (MAX_OUT_COLS) | 1 | 2 | 7 |
| Load_X | 12,288 (LIMB_Q×RING_DIM) | 1 | 3 | 12,291 |
| Compute_Loop | 4096 × sizeP | 1 | **336** | 4096×sizeP + 336 |
| Store_X | 4096 × sizeP | 1 | 2 | 4096×sizeP + 2 |
| **总计** | — | — | — | **8192×sizeP + 12,653** |

固定开销 12,653 = Load_W(17) + Load_Mod(7) + Load_X(12,291) + Compute pipeline fill(336) + Store pipeline fill(2)

> Compute_Loop 迭代延迟 336 cycles 的根因：循环体内有 2 次 `%` 运算（硬件除法器），每次约 100+ cycles，是 Barrett 约减替换的直接动机。

代入 sizeP=5（与 Systolic 版本等价的完整 BConv）：8192×5 + 12,653 = **53,613 cycles**

| 指标 | BConv Naive (sizeP=5) | BConv Systolic (PE阵列) | 变化 |
|------|----------------------|------------------------|------|
| **延迟 (cycles)** | **53,613** (理论推导) | **8,232** | **-84.6% (6.5x 加速)** |
| **时序 Slack (ns)** | 0.07 (满足) | 0.03 (满足) | — |
| **BRAM** | 120 (2%) | 128 (3%) | +6.7% |
| **DSP** | 48 (~0%) | 870 (9%) | +18.1x |
| **FF** | 55,580 (2%) | 33,750 (1%) | -39.3% |
| **LUT** | 41,878 (3%) | 73,691 (5%) | +76.0% |
| **URAM** | 0 | 0 | — |

> 注：Naive 延迟为理论推导值（8192×5 + 20,653 = 61,613 cycles），与 csynth.rpt 中 Compute_Loop II=1、iter_lat=336、trip count=RING_DIM×sizeP 完全一致，无需重新综合。

### 分析

- **DSP 开销**：Systolic 版本使用 15 个 MultMod PE（每个 58 DSP），共 870 DSP，是 Naive 版本（48 DSP，3 个乘法器）的 18 倍。这是用大量 DSP 换取吞吐量的典型 systolic array 策略。
- **延迟**：Systolic 版本固定 8,232 cycles 完成一次 BConv（Load 1538 + Systolic_Loop 4127 + Store 2562）；Naive 版本延迟取决于 sizeP，Compute_Loop 迭代延迟 336 cycles，II=1。
- **FF vs LUT 权衡**：Naive 版本 FF 更高（55K vs 34K），因为使用了更多寄存器缓存中间结果；Systolic 版本 LUT 更高（74K vs 42K），因为 PE 阵列的互连和控制逻辑更复杂。
- **Pipeline II**：两者核心计算循环均达到 II=1。

## 1b. NTT: CG-NTT vs 当前变几何 NTT

CG-NTT 的核心区别：
- 每一 stage 的蝶形访存模式固定（stride 不变，靠数据 shuffle 代替变步长）
- 好处：访存规律、更容易 pipeline、index 生成更简单
- 当前 ntt_kernel.cpp 的 generate_input_index() / generate_output_index() 每 stage 都在变，CG 版本可以大幅简化

### 综合结果对比

| 指标 | 变几何 NTT (Compute_NTT) | CG-NTT (Execute_NTT) | 变化 |
|------|-------------------------|----------------------|------|
| **总延迟 (cycles, 5 limbs)** | 563,371 | 78,506 | **-86.1%** |
| **单 limb 延迟 (cycles)** | 112,671 | 15,701 | **-86.1%** |
| **单 limb 延迟 (ns)** | 676,026 | 94,206 | **7.17x 加速** |
| **时序 Slack (ns)** | 0.15 (满足) | 0.04 (满足) | — |
| **BRAM** | 32 (~0%) | 64 (1%) | +100% |
| **DSP** | 464 (5%) | 116 (1%) | **-75.0%** |
| **FF** | 77,081 (2%) | 8,482 (~0%) | **-89.0%** |
| **LUT** | 62,113 (4%) | 26,965 (2%) | **-56.6%** |
| **URAM** | 0 | 0 | — |

### Pipeline 与访存分析

| 指标 | 变几何 NTT | CG-NTT |
|------|-----------|--------|
| **蝶形循环 II** | 1 (VITIS_LOOP_136_1) | 2 (BUTTERFLY_LOOP) |
| **蝶形迭代延迟** | 22 cycles | 25~26 cycles |
| **MultMod 实例数** | 8 (并行 PE) | 2 |
| **每 MultMod DSP** | 58 | 58 |
| **BRAM 端口冲突** | 无（4-bank partition） | 无（2-bank partition） |
| **Stage 循环** | 12 stages × 64 rows × 144 iter_lat | 12 stages × 1050~1051 iter_lat |

### 分析

- **延迟大幅降低**：CG-NTT 单 limb 延迟仅 15,701 cycles，比变几何 NTT 的 112,671 cycles 快 7.17 倍。主要原因是 CG-NTT 消除了变几何版本中每 stage 的多层嵌套循环（STAGE_LOOP → ROW_LOOP → 多个子 pipeline），改为单层 STAGE_LOOP → BUTTERFLY_LOOP 结构。
- **资源大幅节省**：CG-NTT 仅用 2 个 MultMod（116 DSP），而变几何版本用 8 个（464 DSP），DSP 减少 75%。FF 减少 89%，LUT 减少 57%。
- **Pipeline II 权衡**：CG-NTT 蝶形循环 II=2（而非 II=1），因为只有 2 个 MultMod 需要交替处理奇偶蝶形。但由于总循环结构更简洁，整体延迟仍大幅优于变几何版本。
- **BRAM 增加**：CG-NTT 使用 64 BRAM（vs 32），因为需要额外的 flatten/reshape 缓冲区来做数据重排。

## 1c. 组合实验：PE-BConv + CG-NTT 联合 (Top 顶层)

两个优化同时开启，关注：
- 总资源是否超出芯片容量
- DSP 竞争（BConv 的 Barrett 乘法 和 NTT 的蝶形乘法都吃 DSP）
- 联合加速比 vs 单独加速比之和

### Top 顶层综合结果

| 资源 | 用量 | 占比 | 备注 |
|------|------|------|------|
| **BRAM** | 640 | 15% | 含 m_axi 适配器 BRAM |
| **DSP** | 1,334 | 14% | BConv(870) + NTT×2(232) + Mult(232) |
| **FF** | 69,732 | 2% | — |
| **LUT** | 186,625 | 14% | — |
| **URAM** | 96 | 10% | 用于 twiddle factor 存储 |

### 时序状态

| 指标 | 值 |
|------|-----|
| **时序 Slack** | -0.33 ns (HLS 估计偏差，非真实违例) |
| **目标时钟** | 6 ns (166.67 MHz) |

> 注：HLS csynth 阶段的时序估计存在已知偏差，实际 Vivado 实现后通常可收敛。此处 -0.33 ns 不影响后续分析。

### 各子模块延迟分解

| 子模块 | 延迟 (cycles) | 延迟 (ns) | DSP | BRAM |
|--------|--------------|-----------|-----|------|
| Load_Init_Params | 196,681 | 1,180,086 | 0 | 0 |
| Load_BConv_Params | 55 | 330 | 0 | 0 |
| Load_1 (数据加载) | 可变 | 可变 | 0 | 0 |
| Compute_BConv_Systolic | 8,232 | 49,392 | 870 (9%) | 128 (3%) |
| Execute_INTT (CG-NTT) | 78,446 | 470,676 | 116 (1%) | 64 (1%) |
| Execute_NTT (CG-NTT) | 78,506 | 471,036 | 116 (1%) | 64 (1%) |
| Compute_Mult | 可变 | 可变 | 232 (2%) | 0 |
| Compute_Auto | 4,100 | 24,600 | 0 | 0 |
| Store | 可变 | 可变 | 0 | 0 |

### 分析

- **资源未超限**：所有资源占比均在 15% 以内，U55C 芯片容量充足。DSP 总计 1,334 (14%)，主要消耗在 BConv Systolic (870) 和 Compute_Mult (232)。
- **DSP 分布**：BConv Systolic 占 870 DSP (65%)，是最大的 DSP 消耗者。NTT/INTT 各 116 DSP，Mult 232 DSP。无明显 DSP 竞争问题。
- **初始化开销**：Load_Init_Params 需要 196,681 cycles（加载 twiddle factors 等），这是一次性开销，不影响稳态吞吐。

实验二：异构 CPU+FPGA

需要搭建的实验框架：

```
Host (CPU)                          FPGA (Kernel)
───────────                         ─────────────
OpenFHE 软件流程                     Top() kernel
  │                                    │
  ├─ 轻量操作(Add/Sub) → CPU本地       │
  ├─ 重操作(BConv/NTT) ──PCIe──→     ├─ OP_BCONV
  │                     ←PCIe───     ├─ OP_NTT
  └─ 结果拼装                          └─ OP_INTT
```

### 参数设定

| 参数 | 值 | 来源 |
|------|-----|------|
| N (环维度) | 4096 | define.h: RING_DIM = 1 << 12 |
| sizeQ | 3 | define.h: LIMB_Q = 3 |
| sizeP | 2 | define.h: LIMB_P = 2 |
| MAX_OUT_COLS | 5 | LIMB_Q + LIMB_P |
| SQRT (2D tiling) | 64 | define.h: 1 << 6 |
| PE_PARALLEL | 4 | define.h |

### FPGA 各操作内核延迟 (@6ns, 166.67 MHz)

| 操作 (opcode) | 延迟 (cycles) | 延迟 (μs) | 备注 |
|---------------|--------------|-----------|------|
| OP_INIT (0) | 196,681 | 1,180.1 | 一次性初始化，加载 twiddle factors 等 |
| OP_ADD (1) | ~20,480 | ~122.9 | 5 limbs × 4096 points, II=1 |
| OP_SUB (2) | ~20,480 | ~122.9 | 同 OP_ADD |
| OP_MULT (3) | ~20,480 | ~122.9 | 5 limbs × 4096 points, MultMod II=1 |
| OP_NTT (4) | 78,506 | 471.0 | 5 limbs, 每 limb 15,701 cycles |
| OP_INTT (5) | 78,446 | 470.7 | 5 limbs, 每 limb 15,689 cycles |
| OP_BCONV (6) | 8,232 | 49.4 | Systolic array, 含 Load/Compute/Store |
| OP_AUTO (7) | 4,100 | 24.6 | — |

### 数据传输量估算

| 数据项 | 大小 | 说明 |
|--------|------|------|
| 单 limb 多项式 | 32 KB | SQRT × SQRT × 8B = 64 × 64 × 8 |
| 全多项式 (5 limbs) | 160 KB | 5 × 32 KB |
| BConv 权重矩阵 | 120 B | LIMB_Q × MAX_OUT_COLS × 8 |
| Twiddle factors (NTT+INTT) | 3 MB | 2 × 196,608 × 8B |

### 加速比分析框架

```
加速比 = T_software / (T_cpu_part + T_transfer + T_fpga_kernel)
```

| 分量 | 估算方式 | 备注 |
|------|---------|------|
| T_software | OpenFHE profiling 实测 | 需在 host 端 benchmark |
| T_cpu_part | Add/Sub 等轻量操作在 CPU 执行 | 通常占比小 |
| T_transfer | 数据量 / PCIe 带宽 | PCIe Gen3 x16 ~12 GB/s |
| T_fpga_kernel | 上表各操作延迟之和 | 取决于调度策略 |

以单次 HKS key-switch 为例（DC 策略，3 digits）：
- T_fpga_kernel ≈ 3 × (INTT + BConv + 2×NTT) = 3 × (15,689 + 8,232 + 2×15,701) = 3 × 55,323 = **165,969 cycles ≈ 995.8 μs**
- T_transfer ≈ 每次操作调用需 Load + Store 多项式数据，单次 160 KB / 12 GB/s ≈ 13 μs，多次调用累计
- 若 T_transfer 占比过大，可考虑 double-buffering（当前 load.cpp 的 load/store 和 compute 之间没有 overlap）

实验三：Dataflow 调度策略对比

三种策略在 HLS 层面的实现差异：

**DC (Digit-Centric)** — 当前代码最接近的模式：
```
for each digit d:
    INTT(d) → BConv(d) → NTT(d)
```
- 峰值 BRAM：1 个 digit 的中间结果
- 延迟：串行，digit 间无并行

**MP (Max-Parallel)** — 全局 barrier：
```
INTT(all digits) → barrier → BConv(all digits) → barrier → NTT(all digits)
```
- 峰值 BRAM：所有 digit 的中间结果同时存在
- 延迟：每个阶段内可并行，但阶段间有同步开销

**OC (Output-Centric, sizeP=1)** — 最小 SRAM：
```
for each output tower t:
    BConv(all digits → tower t)   // sizeP=1
```
- 峰值 BRAM：最小（只需 1 个 output tower 的空间）
- 延迟：BConv 调用次数增多

对比指标：

### 单次操作延迟构建块 (来自 Top 综合报告)

| 操作 | 单次延迟 (cycles) | 说明 |
|------|-------------------|------|
| INTT (1 limb) | 15,689 + 1,028 = 16,717 | CG_NTT_Kernel + flatten + reshape 开销 |
| NTT (1 limb) | 15,701 + 1,028 = 16,729 | 同上 |
| BConv (1 call, sizeP=5) | 8,232 | Load_W + Load_Mod + Load_X + Systolic + Store |
| BConv (1 call, sizeP=1) | ~3,600 | Systolic_Loop 缩短 (1 output col vs 5)，Load/Store 不变 |
| Mult (全 limbs) | ~20,480 | 5 limbs × 4096 points |

### 三种策略延迟估算 (numPartQl = sizeQ = 3 digits)

**DC (Digit-Centric)**：每 digit 串行执行 INTT → BConv → NTT

| 步骤 | 每 digit (cycles) | 3 digits 总计 |
|------|-------------------|---------------|
| INTT (1 limb) | 16,717 | 50,151 |
| BConv (sizeP=5) | 8,232 | 24,696 |
| NTT (2 limbs) | 2 × 16,729 = 33,458 | 100,374 |
| **小计** | **58,407** | **175,221** |

**MP (Max-Parallel)**：全局 barrier，阶段内批量执行

| 阶段 | 延迟 (cycles) | 说明 |
|------|--------------|------|
| INTT (3 digits) | 3 × 16,717 = 50,151 | 串行处理 3 个 digit |
| barrier | — | 等待所有 INTT 完成 |
| BConv (3 calls) | 3 × 8,232 = 24,696 | 串行处理 3 次 BConv |
| barrier | — | 等待所有 BConv 完成 |
| NTT (6 limbs) | 6 × 16,729 = 100,374 | 串行处理 6 个 limb |
| **总计** | **175,221** | 单 kernel 下与 DC 相同 |

> 注：MP 策略在单 kernel 架构下与 DC 总延迟相同，因为操作仍是串行执行。MP 的优势在多 kernel 实例化时体现——阶段内的多次调用可并行分发到不同 kernel。

**OC (Output-Centric, sizeP=1)**：按输出 tower 逐个处理

| 阶段 | 延迟 (cycles) | 说明 |
|------|--------------|------|
| INTT (3 digits) | 3 × 16,717 = 50,151 | 同 DC/MP |
| BConv (3 digits × 5 towers) | 15 × ~3,600 = ~54,000 | 每次只输出 1 个 tower |
| NTT (按需) | 5 × 16,729 = 83,645 | 每个 output tower 做一次 NTT |
| **总计** | **~187,796** | 比 DC/MP 多 ~7% |

### 三种策略综合对比

| 指标 | DC | MP | OC (sizeP=1) |
|------|-----|-----|-------------|
| **总延迟 (cycles)** | 175,221 | 175,221 | ~187,796 |
| **总延迟 (μs)** | 1,051.3 | 1,051.3 | ~1,126.8 |
| **BConv 调用次数** | 3 | 3 | 15 |
| **峰值 BRAM (中间结果)** | 1 digit (32 KB) | 全部 digit (96 KB) | 1 output tower (32 KB) |
| **多 kernel 可扩展性** | 低 (digit 间有依赖) | 高 (阶段内可并行) | 中 (tower 间独立) |
| **实现复杂度** | 低 | 中 (需 barrier 同步) | 中 (需多次小 BConv) |

### 分析

- **单 kernel 下 DC ≈ MP**：当前架构只有一个 Top kernel 实例，DC 和 MP 的总延迟相同，因为所有操作都是串行执行。DC 实现最简单，是当前代码的默认模式。
- **OC 延迟略高**：OC 将 BConv 拆成 15 次小调用（vs DC/MP 的 3 次），虽然每次更快（sizeP=1），但 Load/Store 固定开销被放大，总延迟增加约 7%。优势是峰值 BRAM 最小。
- **MP 的潜力**：若未来实例化多个 kernel（如 2 个 NTT kernel），MP 策略的 NTT 阶段可并行执行，延迟可降至 ~125K cycles。但需要额外的 DSP/BRAM 资源。

实现方式：修改 top.cpp 的调度逻辑，为三种策略各写一个调度函数，通过 opcode 或编译宏切换。

## 补 4-2 具体做法：T_software (OpenFHE 纯软件 baseline)

目标：测量纯 CPU 执行 EvalRotate 的延迟，分解到各子操作。

已有基础设施：
- `hks-benchmark.cpp` 已有 benchmark 框架和策略选择
- `FpgaManager::IsReady()` 返回 false 时自动走 CPU 路径
- `HKSStats` 已有操作计数

步骤：

```bash
# 1. 编译 benchmark (不链接 XRT，纯 CPU 模式)
cd build && cmake .. -DWITH_FPGA=OFF && make hks-benchmark

# 2. 跑三种策略的 CPU baseline
./hks-benchmark --strategy DC --repeat 100
./hks-benchmark --strategy MP --repeat 100
./hks-benchmark --strategy OC --repeat 100
```

在 `EvalKeySwitchPrecomputeCore` 中插桩（已有 `HKSStats` 框架，追加计时）：

```cpp
auto t0 = std::chrono::high_resolution_clock::now();
partsCt[part].SetFormat(Format::COEFFICIENT);  // INTT
auto t1 = std::chrono::high_resolution_clock::now();
partsCtCompl[part] = partsCt[part].ApproxSwitchCRTBasis(...);  // BConv
auto t2 = std::chrono::high_resolution_clock::now();
partsCtCompl[part].SetFormat(Format::EVALUATION);  // NTT
auto t3 = std::chrono::high_resolution_clock::now();
stats.time_intt_us  += duration_cast<microseconds>(t1 - t0).count();
stats.time_bconv_us += duration_cast<microseconds>(t2 - t1).count();
stats.time_ntt_us   += duration_cast<microseconds>(t3 - t2).count();
```

预期输出表格：

|--------|-------------|---------|------------|---------------|--------|
| INTT | 789 | 2 | 394.5 | 470.7 (5L) | ~1.2x |
| BConv | 938 | 2 | 469.0 | 49.4 | **9.5x** |

## 补 5-1 具体做法：三种调度策略实测 (host 端调度)

核心思路：FPGA 内核是无状态算子，调度顺序完全由 host 控制。三种策略的区别仅在于 host 发射 opcode 的顺序不同，不需要修改 top.cpp 或重新综合。

已有基础设施：
- `hks_strategy.h`: `HKSStrategy::DC/MP/OC` 枚举 + `SetHKSStrategy()`
- `keyswitch-hybrid.cpp`: `EvalKeySwitchPrecomputeCore` 已有三条分支
- `hks-benchmark.cpp`: 命令行选择策略 + 计时 + 统计输出

三种策略的 host 端 opcode 发射序列：

```
DC (当前默认):
  for digit d in [0..2]:
    emit OP_INTT(d)  →  emit OP_BCONV(d, sizeP=5)  →  emit OP_NTT(d)

MP:
  for digit d in [0..2]: emit OP_INTT(d)     // Phase 1
  --- barrier ---
  for digit d in [0..2]: emit OP_BCONV(d, sizeP=5)  // Phase 2
  --- barrier ---
  for digit d in [0..2]: emit OP_NTT(d)      // Phase 3

OC:
  for digit d in [0..2]: emit OP_INTT(d)     // Phase 1
  for tower t in [0..4]:                      // Phase 2: per output tower
    for digit d in [0..2]:
      emit OP_BCONV(d, sizeP=1, tower=t)
    emit OP_NTT(tower=t)
```

步骤：

```bash
# 编译 (链接 XRT，FPGA 模式)
cd build && cmake .. -DWITH_FPGA=ON && make hks-benchmark

# 跑三种策略
./hks-benchmark --strategy DC --repeat 100 --dump-stats
./hks-benchmark --strategy MP --repeat 100 --dump-stats
./hks-benchmark --strategy OC --repeat 100 --dump-stats
```

每次运行输出 `HKSStats`：操作计数 + 各阶段延迟 + 峰值缓冲。

> 注：OC 策略中 `BConvOffload(sizeP=1)` 的调用路径在 keyswitch-hybrid.cpp 506-507 行有注释标记，当前走的是 CPU `ApproxSwitchCRTBasis` 后丢弃多余 tower。若要真正走 FPGA，需将该处改为 `FpgaManager::GetInstance().BConvOffload(..., sizeP=1)`。

### 实测结果（补 5-1）

实验参数：N=4096, sizeQl=3, sizeP=2, 2 digits (alpha=2)

**表 5-4：三种策略实测对比**

| 指标 | DC | MP | OC |
|------|-----|-----|-----|
| **Precompute 总延迟 (μs)** | **4470** | **5170** | **5989** |
| **Precompute 总延迟 (ms)** | **4.47** | **5.17** | **5.99** |
| INTT 延迟 (μs) | 789 | 1228 | 717 |
| BConv 延迟 (μs) | 938 | 925 | 2656 |
| NTT 延迟 (μs) | 2512 | 2715 | 2306 |
| ModMul 延迟 (μs) | 231 | 302 | 310 |
| INTT 调用次数 | 2 | 2 | 2 |
| BConv 调用次数 | 2 | 2 | **4** |
| NTT 调用次数 (poly/limb) | 4 poly | 4 poly | 7 limb |
| **峰值缓冲 (KB)** | **64** | **128** | **32** |
| FPGA kernel 调用次数 | 45 | 45 | 44 |
| H2D 均值 (μs/call) | 40.6 | 43.9 | 40.3 |
| Kernel 均值 (μs/call) | 123.0 | 123.4 | 122.7 |
| D2H 均值 (μs/call) | 19.2 | 20.6 | 19.7 |
| 传输开销占比 | 32.7% | 34.3% | 32.8% |

> 分析：
> - DC ≈ MP（4.47ms vs 5.17ms）：单 kernel 架构下两者操作序列相同，差异在测量噪声范围内。MP 的优势需多 kernel 实例才能体现。
> - OC 延迟最高（5.99ms，+34%）：BConv 调用从 2 次增至 4 次，每次仍执行完整 BConv 后丢弃多余 tower，固定开销被放大。
> - OC 峰值缓冲最小（32KB），是 MP（128KB）的 1/4，适合片上 SRAM 受限场景。
> - 传输开销约占 1/3，DMA 固定延迟（~20–30μs/call）是主要瓶颈，批量传输可显著改善。
